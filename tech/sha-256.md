# SHA-256 (hash function)

## What it is

A **hash function** turns any amount of data into a short fixed-size fingerprint. **SHA-256** produces 256 bits, written as 64 hexadecimal characters (digits 0 to 9 and letters a to f). Three properties matter: the same input always gives the same fingerprint; changing even one bit of the input changes the fingerprint completely; and you cannot work backward from a fingerprint to an input.

## Why this repository uses it

SHA-256 appears here as a way to name and to verify: recorded model answers are filed under the hash of the request that produced them (so the same request finds the same answer), lock files list the hash of every allowed download, and git names its objects by hash.

## How it works underneath

SHA-256 belongs to the SHA-2 family. It splits the input into 64-byte blocks (padding the last one with the input's length), and mixes each block into a 256-bit state through 64 rounds of fixed bitwise operations (rotations, XOR, additions modulo 2 to the power 32). Because the final state depends on every bit of every block, any change spreads. You cannot find two different inputs with the same output by anything better than astronomical luck, which is why equality of fingerprints is taken as equality of content.

Two practical details. First, hashes are computed over **bytes**, never over text, so you must say how text becomes bytes; here always UTF-8 (`.encode("utf-8")`). Second, a hash is not encryption and not a password store: it hides nothing about inputs that can be guessed.

## Walkthrough of this repository's use

### The fixture key

`src/guard_redteam/domain/llm.py`

<!-- fmt: off -->
```python
    def fixture_key(self) -> str:
        """A stable hash of the request; the Java port computes the same string, so both read one fixture file."""
        parts = [
            self.model,
            f"{self.temperature:.3f}",
            str(self.max_tokens),
            "-" if self.seed is None else str(self.seed),
            *(f"{m.role}\x1f{m.content}" for m in self.messages),
        ]
        return hashlib.sha256("\x1e".join(parts).encode("utf-8")).hexdigest()
```
<!-- fmt: on -->

This method belongs to the request object that is sent to a chat model.

- `parts = [...]` builds a list of text pieces: the model name; the temperature printed with exactly three decimals (`.3f`), so 0.2 and 0.20 give the same text; the maximum number of reply tokens; the seed, or a dash when there is none; then one piece per message, each `role`, a `\x1f` separator, and the content.
- `"\x1e".join(parts)` glues the pieces with the ASCII *record separator* character. Neither separator occurs in ordinary text, so two different requests cannot accidentally produce the same joined string.
- `.encode("utf-8")` turns the text into bytes.
- `hashlib.sha256(...)` is Python's standard-library implementation; `.hexdigest()` returns the 64 hexadecimal characters.

The recorded fixtures are stored one JSON line per answer under this key. The Java code computes the same key (the comment in the docstring says so), so Python and Java read one file.

### Hashing the evidence

`src/guard_redteam/interfaces/cli.py`

<!-- fmt: off -->
```python
def _sha256(path: Path) -> str:
    return hashlib.sha256(path.read_bytes()).hexdigest()
```
<!-- fmt: on -->

Reads the whole file as bytes and hashes it. `cmd_evidence` stores these hashes of the data, prompts, limits and fixtures in `evidence/`, so a reviewer can tell whether the files used in the run are the same as the ones in the repository.

## Try it yourself

1. `printf 'abc' | shasum -a 256` prints `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad` followed by `-`. That is the well-known test vector for the text `abc`.
2. `printf 'abd' | shasum -a 256` changes one letter and the entire fingerprint changes.
3. `python3 -c "import hashlib; print(hashlib.sha256(b'abc').hexdigest())"` prints the same value as the first command.
4. `shasum -a 256 requirements.lock` prints the fingerprint of the lock file (compare after any edit).
5. `grep -m1 -o 'sha256:[0-9a-f]\{64\}' requirements.lock` shows one hash from the lock file: 64 hexadecimal digits.

## Mistakes people make

- **Hashing text without saying how it becomes bytes.** Two programs must use the same encoding.
- **Ambiguous joins.** Joining `a`,`bc` and `ab`,`c` with nothing in between gives the same string; hence the separator characters.
- **Using a fast hash for passwords.** SHA-256 is for fingerprints; passwords need slow, salted schemes.
- **Comparing only a prefix** of the hash and calling it verified.
- **Believing a matching hash means a trustworthy file.** It means the file is the one you pinned; you still have to trust where the pin came from.

## Check yourself

1. **How long is a SHA-256 fingerprint?**  
   256 bits: 64 hexadecimal characters.
2. **If two files have the same SHA-256, what do we conclude?**  
   That they are the same content.
3. **Why does `fixture_key` join its parts with separator characters?**  
   So that different requests cannot produce the same joined text.
4. **Why must text be encoded before hashing?**  
   The hash works on bytes, so the encoding (UTF-8 here) must be fixed.
5. **Can you recover the input from the hash?**  
   No, the function cannot be run backward.
