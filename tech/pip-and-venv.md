# pip, virtual environments and hash-pinned lock files

## What it is

**pip** is Python's installer: it downloads libraries from the Python Package Index (PyPI) and puts them where Python can import them. A **virtual environment** (venv) is a private folder (here `.venv`) with its own Python and its own installed libraries, so one project's libraries cannot clash with another's. A **lock file** lists every library with the exact version and the fingerprint (hash) of the files you trust.

## Why this repository uses it

A reader must be able to get *exactly* the libraries that produced the committed numbers, on a clean machine, and be warned if anything changed. `.venv` isolates the project, `pyproject.toml` says what the code needs in loose terms, and `requirements.lock` / `requirements-dev.lock` say what was actually installed (7 libraries for running, 48 for development). pip is told to refuse any file whose hash is not in the lock file.

## Where it appears

| File | What it does with this technology |
| --- | --- |
| `pyproject.toml` | Loose dependency rules and the project's name; pip reads it for `pip install -e .`. |
| `requirements.lock` | Runtime libraries with exact versions and hashes. |
| `requirements-dev.lock` | Runtime plus development tools (ruff, mypy, pytest, ...), same format. |
| `Makefile` | `make install` and `make lock` run pip and uv. |


## How it works underneath

**How Python finds libraries.** `import x` searches the folders listed in `sys.path`. A venv has its own `site-packages` folder at the front of that list. `python -m venv .venv` copies (or links) a Python interpreter into `.venv/bin/python` and creates an empty `site-packages`. Running `.venv/bin/python` (or `.venv/bin/pip`) therefore uses that private world. Activating the venv (`source .venv/bin/activate`) only edits your shell's `PATH` so the short names `python` and `pip` point there; this repository never needs to activate, because the Makefile calls `.venv/bin/...` directly.

**What pip does.** `pip install name` asks PyPI which files exist for `name`, picks a **wheel** (a ready-to-unpack zip, `.whl`) that fits your Python and operating system, falls back to a source archive if there is none, resolves the libraries it depends on, downloads, and unpacks into `site-packages`.

**Editable install.** `pip install -e .` installs *this project* by linking to `src/` instead of copying it, so edits take effect at once. `--no-deps` says: do not resolve dependencies now; they were already installed from the lock file.

**Lock files and hashes.** A line like `httpx==0.28.1 --hash=sha256:...` fixes the version and lists the SHA-256 (`sha-256.md`) of each allowed file. With `--require-hashes` pip refuses any package that is not pinned with a hash and any file whose hash differs. The lock files here are produced by **uv** (`uv pip compile --universal --generate-hashes`): uv is a fast resolver that works out one set of exact versions that is valid on macOS, Linux and Windows (`--universal`). The "# via" comments show who needed each library.

## Walkthrough of this repository's use

### Creating the environment

`Makefile`

```make
$(STAMP): requirements-dev.lock pyproject.toml
	$(PYTHON) -m venv $(VENV)
	$(VENV)/bin/pip install -q --require-hashes -r requirements-dev.lock
	$(VENV)/bin/pip install -q --no-deps -e .
	touch $@
```

A **stamp file**: `.venv/.installed` is the target, and make re-runs the recipe whenever the lock file or `pyproject.toml` is newer than the stamp. `$(PYTHON) -m venv $(VENV)` creates the environment. `pip install -q --require-hashes -r requirements-dev.lock` installs exactly the locked libraries and refuses anything unhashed (`-q` quiet, `-r` read the list from a file). `pip install -q --no-deps -e .` installs this project in editable mode without touching the libraries. The last line (`touch`) refreshes the stamp date.

### The lock file format

`requirements.lock`

```text
# This file was autogenerated by uv via the following command:
#    uv pip compile pyproject.toml --universal --generate-hashes --python-version 3.12 -o requirements.lock
anyio==4.15.1 \
    --hash=sha256:6152fdbbf9a77fdec97731721bebf7c4c44f7c29b424b0065826173efc7ed101 \
    --hash=sha256:9f28306018cbd6d329e64a36d58256edff76dd996fe423bc957326e578b82a94
    # via httpx
certifi==2026.10.23 \
    --hash=sha256:a9895e6e2758b371e0545e321a3a8fd1fcfd9829ada8824a936dfb16aaaf36cd \
    --hash=sha256:e9b54de76e530bb6cf0ccd036787103acb58fd42ba930ea8bf948ddbaa2f61d1
    # via
    #   httpcore
    #   httpx
```

- The first two lines are written by uv and record the exact command that made the file, so anyone can regenerate it.
- `anyio==4.15.1 \` is the library, `==` means exactly that version, and the trailing backslash continues the line.
- Each `--hash=sha256:...` is the fingerprint of one downloadable file (one per platform build or source archive). pip accepts a file only if its hash is in this list.
- `# via httpx` records which other library required this one, which helps you decide whether it can be removed.

### Regenerating the locks

`Makefile`

```make
lock: ## regenerate requirements.lock and requirements-dev.lock (needs uv)
	uv pip compile pyproject.toml --universal --generate-hashes --python-version 3.12 -o requirements.lock
	uv pip compile pyproject.toml --universal --generate-hashes --python-version 3.12 --extra dev -o requirements-dev.lock

check: lint test ## everything that needs no services
```

`make lock` runs uv to resolve `pyproject.toml` again and rewrite the lock files. It is the only way the pinned versions should change, and the change appears in a commit you can review.

## Try it yourself

1. `make install` creates `.venv` (about a minute the first time). When it finishes, `ls .venv/bin | head` lists `python`, `pip`, `ruff`, `pytest`, ...
2. `.venv/bin/python -c "import sys; print(sys.prefix)"` prints a path ending in `/.venv`: Python knows it is inside the environment.
3. `.venv/bin/pip list | head` lists the installed libraries; compare a version with `grep '^httpx==' requirements.lock`.
4. `grep -c -- '--hash=sha256' requirements.lock` counts the hash lines (several per library).
5. `.venv/bin/pip install --require-hashes httpx==0.28.1` fails with a message that hashes are missing: pip will not install an unpinned request in hash mode.

## Mistakes people make

- **Running `pip install` with the system Python.** It changes the machine-wide set of libraries; use `.venv/bin/pip`.
- **Committing `.venv`.** It is huge and machine-specific; it is in `.gitignore`.
- **Editing the lock file by hand.** The hashes would no longer match. Edit `pyproject.toml` and run `make lock`.
- **Expecting `==` in `pyproject.toml`.** There the rules are loose (`>=`), by design; exactness belongs in the lock.
- **Mixing a venv made with one Python and running with another** after a Python upgrade: delete `.venv` and `make install` again.

## Check yourself

1. **What does a virtual environment isolate?**  
   The installed libraries (and the Python interpreter copy) of one project from all others.
2. **What does `--require-hashes` guarantee?**  
   Only files whose SHA-256 appears in the lock file are installed; any other file is refused.
3. **Why is `pip install -e .` used?**  
   It installs the project by link, so source edits take effect without reinstalling.
4. **What is a wheel?**  
   A prebuilt package archive (`.whl`) that pip can unpack without compiling.
5. **Which file do you edit to change a dependency, and what do you run next?**  
   `pyproject.toml`, then `make lock`.
